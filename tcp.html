TCP ── つないで、確実に届ける

相手のIPアドレスがわかったので、いよいよ手紙を送ります。でもインターネットは、途中でデータがなくなったり、順番が入れかわったりする道です。そんな道の上で「確実に、順番どおりに届ける」約束をしてくれるのが TCP です。

3.1ブラウザはOSに「つないで」と頼む

ブラウザは、データを送る仕組みを自分では持っていません。DNSのときと同じように、OSに頼みます。頼むときの窓口をソケットと呼びます。電話にたとえると、受話器を用意して、番号を押して、話して、切る、という流れです。

1 / 6
ブラウザ
OS（TCPの係）

ブラウザが頼むのは「つないで」「送って」「受け取って」「切って」だけです。再送や順番の並べ直しといった面倒な仕事は、すべてOSの中のTCPが引き受けます。この章では、その中身をのぞいていきます。

3.2ポート番号 ── 住所の中の部屋番号

IPアドレスは「どのコンピュータか」を表す住所でした。でも1台のPCでは、ブラウザ、メール、音楽アプリなどがいっせいに通信しています。届いたデータをどのアプリに渡すかを決めるのがポート番号です。住所の中の部屋番号のようなものです。

ブラウザのタブを開いてみましょう。タブごとに新しいつながりができ、PC側には空いている部屋番号が1つずつ割り当てられます。

あなたのPC 192.168.1.23
相手のサーバー
自分のIP自分のポート相手のIP相手のポートアプリ

↑ ボタンを押すと、つながりが1つずつ増えていきます。

サーバー側は「決まった部屋番号」

サーバーは、だれからでも見つけてもらえるように、決まった番号で待っています。HTTPSは 443、HTTPは 80、DNSは 53 です（1.2で見た「決まりの番号」と同じです）。0〜1023番は、こうした代表的な仕事のために決められています。

PC側は「その場かぎりの部屋番号」

PC側の番号は、つなぐたびにOSが空いている番号から選びます。IANA（番号を管理する団体）の決まりでは 49152〜65535 番で、Mac もこの範囲を使います（OSによって範囲は少し違います）。4つの値の組み合わせ（自分と相手のIP・ポート）で、つながりを1本ずつ見分けます。

3.33ウェイハンドシェイク ── つなぐ前のあいさつ

TCPは、データを送る前に相手と3回のあいさつを交わします。「話してもいい？」「いいよ、こっちもいい？」「いいよ」。この間に、おたがいの通し番号の始まりを伝え合います。番号は、あとで「どこまで届いたか」を確かめるのに使います。

0 / 4
あなたのPCCLOSED
サーバーLISTEN

あいさつには、1往復半かかります。PCがデータを送り出せるのは3回目のあいさつと同時なので、つなぐだけで1往復分の時間がかかる、と考えればよいでしょう。相手が遠いほど、この1往復が重くなります。

※ 通し番号の始まりは、本当は推測されにくいように毎回ランダムに決めます（RFC 6528）。ここでは見やすいように 1000 と 5000 にしています。

3.4データを小分けにして、番号をふる

大きなデータは、そのままでは送れません。TCPは、データをセグメントという小さなかたまりに分け、1つ1つに通し番号（シーケンス番号）をつけます。番号は「データの先頭から何バイト目か」を表します。送るデータの大きさを変えてみましょう。

1つのセグメントに入れられる中身の上限を MSS と呼びます。ふつうのイーサネットでは、1回に運べる大きさ（MTU）が1500バイトです。そこからIPの見出し（IPv4は20バイト、IPv6は40バイト）とTCPの見出し（20バイト）を引いた 1460バイト（IPv6なら1440バイト）が、よく使われるMSSです。

3.5届いたら「受け取ったよ」、届かなければ送り直す

受け取った側は、「ここまで届いたので、次は○番からください」という返事（ACK）を返します。送った側は、ACKが来なければ、なくなったと考えて送り直します。途中で1つなくしてみましょう。

送る側（サーバー）受け取る側（PC）
PCが組み立てたデータ

同じACKが3回来たら、すぐ送り直す

3番目がなくなると、PCは4番目・5番目が届いても「次は3番目のデータをください」と同じACKをくり返します。送る側は、同じACKが3回重なったら（元のACKと合わせて4回）、タイマーを待たずにすぐ送り直します。これを高速再送と呼びます。

だれも返事をくれないときは

ACKがまったく来ないときは、タイマーが切れるのを待って送り直します。待ち時間は、それまでの往復の時間から計算します。まだ1回も測っていないときの最初の値は1秒で、送り直すたびに2倍にのばしていきます（RFC 6298）。

3.6ウインドウ ── 返事を待たずに、まとめて送る

1つ送ってACKを待ち、また1つ送って待つ……では、往復の時間ばかりかかってしまいます。そこでTCPは、ACKを待たずに送ってよい量を決めて、まとめて送ります。この量をウインドウと呼びます。ウインドウと往復の時間を変えて、どれだけの速さで送れるか見てみましょう。

送る側受け取る側
最高の速さ5.2Mbps
1GBを送るのに27分

速さの上限は、ざっくり ウインドウ ÷ 往復の時間 で決まります。往復が長い（相手が遠い）ほど、ウインドウを大きくしないと速く送れません。昔のTCPではウインドウの最大は64KBでしたが、今は「何倍にするか」を伝える仕組み（ウインドウスケール、RFC 7323）で、最大1GBまで広げられます。

ウインドウの大きさは、受け取る側が「あとこれだけなら受け取れる」と毎回のACKに書いて知らせます。受け取る側の手が回らないときは小さくして、送る側にゆっくり送ってもらいます。

3.7混雑をよける ── 輻輳制御

受け取る側に余裕があっても、途中の道が混んでいることがあります。全員が全力で送ると、道があふれてデータがどんどん捨てられてしまいます。そこでTCPは、道の混み具合を探りながら送る量を調整します。これを輻輳（ふくそう）制御と呼びます。

はじめは少しだけ送り、ACKが返ってくるたびに送る量を倍々で増やします（スロースタート。最初は10セグメントから始めるのが今の標準です。RFC 6928）。ある程度まで来たら、ゆっくり増やします。データが捨てられたら「混んでいる」と考えて、送る量を大きく減らします。

今、Linux や Windows で標準になっている CUBIC（RFC 9438、2023年）は、減らす量を控えめにし、前に混んだ量の近くまで素早く戻ってから、慎重に探るのが特徴です。

3.8確実さより速さ ── UDP

TCPのほかに、もう1つの運び方 UDP があります。UDPは、あいさつも、ACKも、送り直しもしません。投げたら投げっぱなしです。そのぶん、手間がなく速く届きます。同じ5つのデータを、途中で1つなくしながら送ってみましょう。

TCP
UDP

TCPは、なくした3番を送り直してもらうまで、4番と5番をアプリに渡せずに待ちます。UDPは届いた順にすぐ渡し、なくした3番はそのままです。

TCPUDP
つなぐ前のあいさつする（1往復）しない
なくなったら送り直すそのまま
順番並べ直して渡す届いた順
おもな使い道Webページ（HTTP/1.1・2）、メール、ファイルの転送DNS、ビデオ通話、オンラインゲーム、HTTP/3（QUIC）

ビデオ通話で少し前の映像が届いても役に立たないように、遅れて届くくらいなら、捨ててくれた方がよい使い道ではUDPが選ばれます。第1章で見た HTTP/3 の QUIC も、UDPの上に「送り直し」や「暗号化」を自分で作りこんだ仕組みです。TCPをOSの中で作りかえるのは時間がかかるので、アプリの側で新しい運び方を作れるUDPが土台に選ばれました。

3.10まとめ

  • ブラウザは ソケット を通してOSに「つないで・送って・受け取って・切って」と頼む。面倒な仕事はOSの中のTCPが引き受ける
  • ポート番号は住所の中の部屋番号。サーバーは決まった番号（443など）、PCはその場かぎりの番号（49152〜65535）を使う
  • つなぐ前に 3ウェイハンドシェイク（SYN → SYN+ACK → ACK）で、通し番号の始まりを伝え合う。1往復分の時間がかかる
  • データは MSS（よく使うのは1460バイト）ごとに分けて、シーケンス番号をふる
  • 受け取った側は ACK で「次は○番から」と返す。なくなったら、同じACKが3回重なるか、タイマーが切れたら送り直す
  • ウインドウの分だけ、ACKを待たずにまとめて送る。速さの上限は ウインドウ ÷ 往復の時間
  • 輻輳制御で、道の混み具合を探りながら送る量を増やしたり減らしたりする
  • UDP は送り直しをしないぶん速い。DNS・ビデオ通話・HTTP/3 の土台に使われる

これで、データを確実に届ける約束ができました。でも、このままでは途中の人に中身を読まれてしまいます。次の章では、手紙に鍵をかけて送る HTTPS を見ていきます。
